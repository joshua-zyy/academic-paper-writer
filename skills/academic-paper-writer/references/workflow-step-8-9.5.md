# 主线、分节写作与图表

## 1. 主线确认

主 agent 根据首轮材料建立 section_blueprint：研究问题、核心想法/贡献、现有结果、论证链、章节职责、证据 ID 与缺口。全文或重大重构在起草前集中请作者确认；作者明确委托决定时记录委托范围，不伪装作者点击确认。局部任务复用既有主线，仅主张重大变化时再问。

章节 ID 使用 introduction、related_work、method、experimental_setup、results、discussion、conclusion、abstract。按 venue 和论文类型合并/省略章节，消融是 results 子单元，不强制单列。

## 2. 写作前检查

读取当前节所需指南，问：读者需要理解什么？现有证据覆盖哪些论点？还缺哪个具体事实？充分则直接写；不足则只派发定向补查，不固定三 Task，不复制全部历史上下文。

补查失败或确实无材料时，写已支持的正文、其余有说明的框架并列建议。Introduction/RW 零可用引文时也可规划论证功能与检索方向，不硬造领域事实或文献综述。

## 3. 主 agent 写正文

- 用正常论文 prose 表达已有实质内容。框架部分明确标示，不用长篇空话冒充正文。
- 数字、方法与引文关联来源记录；`newly_run`、路径、审查状态等内部注记只放 evidence_inventory，不附在论文句子后。
- Method 写清操作、输入输出与数据流。作者设计意图可以忠实表达；代码本身不能证明设计动机。公式按实际机制需要，不强制每模块至少一个公式或边界句。
- Results 组织主问题及关键比较，不逐条复述表格；相同数字的正文、图注、表格口径一致。
- Discussion 解释与原文支持范围对齐，区分观察与假设；局限集中、具体且适度，不在其他段落反复声明“尚不能证明”。
- 主笔内化 academic-polishing，按论证功能补缺、压缩或重排，不用段落配额判断 thin draft。

## 4. 图表

每个图/表有用途、来源、必须呈现内容与 caption；不为每个模块、结果表强制配图。

数据够且图能帮助论证时派发 academic-figure：mode `chart-from-data`，指定 evidence_ids、源数据、口径、单位、图用途、输出路径与图注要求。子代理可在分配目录创建 Python 脚本和 SVG，不修改正文或实验数据。允许在章节写作中生成并检查，不拖到全文最后才运行。

数据缺失返回 figure-blueprint 与待补项，不造数值。架构图/机制图只检查作者提供的图或记录 `manual_figure_needed`（用途、来源、模块/连接、caption），不自动绘制或生图。

主 agent 整合图引用与图注，核对来源、数字和图面实际内容。绘图失败不会让独立章节停摆；不能以仅有脚本宣称图已交付。

## 5. 保存与章节验收

正文默认写入 paper_draft.md，只维护一份 References，末尾统一待补清单。更新相关来源与状态，不在多个步骤重复追加同一段。

交给 academic-reviser 当前节、相关已写上下文、版本、证据/引文/图表定位与预期范围。验收者只返回问题，主 agent 修订；详见 workflow-step-9.6-12.md。章节内容不足时也检查其已有内容，不假装完整章节通过。
